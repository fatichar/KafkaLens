Remote Access (gRPC Backend)

Browse clusters inside private networks — without exposing your brokers.

How it works

KafkaLens ships a small backend service (GrpcApi) that runs inside your network, next to your Kafka brokers. It exposes a read-only gRPC API. The desktop app connects to the backend; the backend is the only component that talks to Kafka. 


┌─────────────┐   gRPC (HTTP/2)  ┌───────────────────┐   Kafka protocol  ┌────────┐
│  KafkaLens  │ ◄──────────────► │ KafkaLens backend │ ◄───────────────► │ Kafka  │
│  (desktop)  │                  │   (GrpcApi)       │                   │ brokers│
└─────────────┘                  └───────────────────┘                   └────────┘
  your machine                      inside the VPC                         private
  • Brokers are never exposed outside the private network.
  • The API is read-only — the backend can browse and fetch messages, nothing else.
  • Clusters are registered on the backend, so every connected desktop sees the same list.

Deploying the backend

The backend is an ASP.NET Core service in the KafkaLens repository (GrpcApi/). Building it requires the .NET 10 SDK; the output is a self-contained single file that needs no runtime on the target machine. 

# from the GrpcApi directory
dotnet publish GrpcApi.csproj -c Release -r linux-x64 \
    -o grpc_api/ -p:PublishSingleFile=true -p:PublishTrimmed=true

# on the server
./GrpcApi

By default it listens on port 8080 (plain HTTP/2) on all interfaces. Run it on a host that can reach your bootstrap servers — same VPC or subnet is typical.

Verify it works from a desktop machine before wiring everything up: add it as a client in the app (below) — a successful connection means routing and firewall rules are right.

Configuration

Settings come from appsettings.json, environment variables, or command-line arguments (standard .NET configuration): 

{
  "DatabasePath": "cluster_info.json",
  "Kestrel": {
    "EndpointDefaults": { "HttpPort": 8080 }
  },
  "GrpcFetch": {
    "MaxMessagesPerRequest": 25000,
    "MaxConcurrentFetches": 12,
    "QueueTimeoutMs": 5000,
    "FetchTimeoutMs": 120000
  }
}
SettingDefaultMeaning
DatabasePathcluster_info.jsonPath to the cluster registry file (see below).
Kestrel:EndpointDefaults:HttpPort8080Port the gRPC endpoint listens on.
GrpcFetch:MaxMessagesPerRequest25000Cap on messages streamed per fetch request.
GrpcFetch:MaxConcurrentFetches12Max simultaneous fetches across all connected clients.
GrpcFetch:QueueTimeoutMs5000How long a fetch waits for a free slot before failing.
GrpcFetch:FetchTimeoutMs120000Maximum duration of a single fetch.

Environment-variable equivalents use the standard mapping, e.g. Kestrel__EndpointDefaults__HttpPort=9000.

Registering clusters on the backend

The backend reads its cluster list from the JSON file at DatabasePath: 

{
  "clusters": [
    { "id": "prod",    "name": "Production", "address": "kafka1:9092,kafka2:9092" },
    { "id": "staging", "name": "Staging",    "address": "staging-kafka:9092" }
  ]
}

Each entry needs a unique id, a display name, and an address (bootstrap servers, comma-separated). Edit the file and restart the service to pick up changes. These clusters then appear to every desktop that connects.

Connecting the desktop app

  1. Open Cluster → Edit Clusters (Ctrl+E) → KafkaLens Clients tab → Add.
  2. Enter a name (e.g. Prod VPC), the backend address as host:port (e.g. 10.0.3.15:8080 — http:// is added automatically), and keep the protocol as grpc.
  3. OK, then Save.
  4. The backend's clusters now appear under Cluster → Open Cluster, marked with live status dots like any direct cluster.

From there, everything works the same as a direct cluster — topics, fetches, formatters, filters, saving.

Security notes

The gRPC endpoint is plaintext HTTP/2 — there is no TLS or authentication built in. Treat it accordingly:

  • Bind it inside the VPC only. Restrict the port with security groups / firewall rules so only the intended desktops (or a bastion/VPN gateway) can reach it.
  • For crossing untrusted networks, put the backend behind a TLS-terminating reverse proxy (nginx, Envoy) or reach it over a VPN/SSH tunnel.
  • Read-only ≠ harmless. The API can't modify the cluster, but it can read every message — restrict access like you would the brokers themselves.

Operations

  • Logs — the service logs to stdout; capture it with your service manager (systemd, supervisor) or a container platform.
  • Fetch pressure — if many users fetch at once, tune GrpcFetch limits; rejected fetches show up as fetch errors in the desktop app's log.
  • Updates — redeploy the published binary and restart. The desktop and backend are versioned together, so upgrade them in pairs.
